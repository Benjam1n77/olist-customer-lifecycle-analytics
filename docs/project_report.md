# Olist 电商客户生命周期与精细化运营分析 — 分析与实施报告

> 本报告说明数据模型、分析方法、实测结果、质量验证与运营应用。
> 11 项核心宽表指标通过 SQL × Python 交叉验证；专题结果来自数据库查询与分析脚本，来源见 [指标索引](verified_metrics.md)。
> 观察日 analysis_date = 2018-08-30（最大有效购买日期 + 1 天，由数据推导）。

---

## 一、项目概述

### 1.1 背景与目标

基于 Kaggle 公开数据集 Brazilian E-Commerce Public Dataset by Olist（实际购买时间覆盖 2016 年 9 月 – 2018 年 8 月，99,441 笔订单），独立完成一个可复现、可展示的数据分析项目，回答七个业务问题：

| # | 业务问题 | 最终答案（实测） |
| --- | --- | --- |
| 1 | 一次性购买是否严重 | 是，一次性购买占比 97.00% |
| 2 | 首购后留存表现 | 21 个成熟 Cohort 的加权 M1 留存率为 0.48%（390 / 81,265） |
| 3 | 高价值流失用户 | 10,915 人，历史支付占比 30.89% |
| 4 | 配送延迟是否影响评分 | 延迟订单评分下降 40.24%，控制混淆后关联仍显著（OR=11.35） |
| 5 | 首购后 90 天二购的关联因素 | 成熟客户跨日二购率 1.2969%；多商品正向关联、首单低评分负向关联 |
| 6 | 营销人群名单 | 6 条互斥规则产出 71,424 人分层名单 |
| 7 | 看板与实验支持 | 3 页 Tableau 看板数据 + 2 个 A/B 测试设计 |

### 1.2 技术栈与分工

- **技术栈**：Python 3.13、MySQL 8.0.44、pandas、matplotlib/seaborn、SQLAlchemy/PyMySQL、scipy/statsmodels、pytest、Tableau。
- **分工原则**：SQL 负责建模与指标计算（口径固化、可复现）；Python 负责导入、校验、统计检验、可视化与导出；核心逻辑全部在 `src/`，Notebook 仅做展示。

### 1.3 分析流程

从原始数据到分析交付的依赖关系如下：

```text
数据字典与关系建模 → 导入与质量检查 → 订单宽表 → 用户宽表
→ 标签分层 → Cohort 留存 / 履约体验 / 90 天二购专题
→ 营销人群 → 图表、Tableau 与展示 Notebook
质量检查、指标交叉验证与自动化测试贯穿各环节。
```

## 三、数据理解、数据字典与建表

### 实现方式

1. **先检查真实数据再写文档**：逐一读取 9 个 CSV 的表头、行数与样例值，所有字典内容基于实际观察；
2. 编写 `docs/data_dictionary.md`：9 张表的粒度、主键/候选键、外键、字段类型建议、业务含义、质量风险、是否进入核心分析，并明确 7 条表关系；
3. 编写 `docs/er_diagram.md`：Mermaid ER 图 + 关系基数表；
4. 编写 `sql/01_create_database.sql`（utf8mb4 建库）与 `sql/02_create_tables.sql`（9 张表 DDL）：
   - 字段名与 CSV 表头完全一致（便于导入）；
   - 金额 DECIMAL(10,2)、时间 DATETIME、评分 TINYINT；
   - `order_items` / `order_payments` 使用复合主键；
   - 为关联与查询字段建立索引；
5. 建库建表 SQL 已实际执行验证；重建时会删除并重新创建目标表，须使用专用项目数据库。

### 关键决策

- **逻辑外键而非物理外键**：原始数据可能存在孤立记录，物理约束会阻止导入；关联完整性由质量检查量化验证（结果为 100% 完整）；
- **geolocation（100 万行）不入核心宽表**：邮编存在重复坐标，直接使用会多对多膨胀；客户/卖家表已自带城市与州字段，满足地区分析需求。

## 四、数据导入与质量检查

### 4.1 数据导入

- 导入采用 **pandas 读取 + executemany 批量插入**（每 5,000 行一批）；
- **评价表的记录解析与去重**：
  1. `olist_order_reviews_dataset.csv` 的评价文本含**内嵌换行符**：物理行数 104,719 ≠ 实际记录数 99,224。**统计 CSV 记录数需使用解析器，不能将 wc -l 的物理行数视为记录数**；
  2. CSV 中存在 **789 个重复 review_id**：764 个出现 2 次、25 个出现 3 次，共 814 条多余记录。重复组除 order_id 外字段一致并关联至同一真实客户；该模式与同一问卷关联多笔订单的解释相容，但不能据此确认平台内部机制。导入时用 `INSERT IGNORE` 保留每个 ID 的首条记录，被丢弃的 814 行留档至 `data/interim/dropped_duplicate_reviews.csv` 供审计。

### 4.2 质量检查（34 项）

编写 `sql/03_data_quality_checks.sql`，覆盖主键唯一性 / 空值 / 枚举值 / 时间逻辑 / 数值合理性 / 关联完整性 / 多重记录七大类，产出 `docs/data_quality_report.md` 与 `outputs/tables/data_quality_summary.csv`。

主要结论：

| 检查类 | 结果 |
| --- | --- |
| 主键唯一性 | 全部通过 |
| 关联完整性 | F1–F5 核心关联无孤立记录；F6 有 13 个类别缺少英文翻译 |
| 有效订单 | delivered 96,478 笔（97.02%） |
| 时间逻辑 | D2 审批晚于承运 1,350 条（1.40%）；经核实 delivery_days/delay_days 不使用审批/承运商时间，故不排除，仅记录 |
| 数值合理性 | 9 条支付金额≤0、4 件商品重量≤0，记录但未作为核心分析的额外过滤条件 |
| 金额口径 | item_amount 与 payment_amount 存在 260 笔差异>0.05 元，两者分别保留 |

### 4.3 口径与边界校验

- 异常占比采用 `SUM(布尔条件)/COUNT(*)`，分母覆盖全部检查对象，不能先筛出异常行再求占比；
- 全状态数据中，**跨订单客户数为 2,997 人**，3,345 是"多余 customer_id 数"（一人 3 单贡献 2 个多余 ID），两者不可混用；
- 2,965 条签收时间空值中，仅 8 条属 delivered 订单，其余 2,957 条来自未交付订单；缺失值应按订单状态解释。

## 五、订单粒度宽表（mart_order_summary）

### 实现方式

严格遵循"先聚合再 JOIN"原则（商品/支付/评价对订单均为一对多，直接 JOIN 会行数膨胀）：

1. `sql/04` → `order_item_agg`（98,666 行）：item_count、distinct_product_count、seller_count、goods/freight/item_amount、main_category（商品金额最高的类别，并列取字典序保证确定性）；
2. `sql/05` → `order_payment_agg`（99,440 行）：payment_amount、main_payment_type、max_installments；
3. `sql/06` → `order_review_agg`（98,167 行）：同单多评价（243 单）取最高分，规则写入注释与指标文档；
4. `sql/07` → `mart_order_summary`（99,441 行 × 32 字段，一行一订单），含 delivery_days / delay_days / is_delayed / is_low_score 派生字段。

### 验证

- 粒度：99,441 行 = orders 行数，一行一订单 ✓；
- 金额：支付总额聚合前后精确一致（16,008,872.12 BRL）✓；
- 金额差异检查：98,665 笔双金额齐全订单中 98,089 笔完全相等，260 笔差异>0.05 元（241 笔支付偏多、19 笔偏少，最大差 182.81 元），已量化记录。

### 边界处理

1,267 笔"当天超时"订单的签收时间戳晚于预计时间，但日期相同（delay_days=0）；这些订单归入延迟 1-3 天档。

## 六、用户粒度宽表（mart_customer_features）

### 实现方式

构建一行一个 `customer_unique_id` 的用户宽表（93,358 行 × 22 字段），覆盖首末购时间、tenure、recency、order_count、金额、AOV、偏好类别/支付方式、履约与评价体验指标、地区。

### 关键口径（均已写入指标文档）

- **analysis_date = 2018-08-30**：最大有效购买日 2018-08-29 + 1 天，数据推导非手工指定；
- 仅纳入至少一笔 delivered 订单的客户（93,358 人）；2,738 个零有效订单客户排除，勾稽关系 96,096 = 93,358 + 2,738 已记录；
- favorite_category 采用**消费金额口径**（商品明细级 SUM(price)）；customer_state 采用**最近订单口径**（同日按 order_id 字典序确定性取一）；
- recency_days = DATEDIFF(analysis_date, last_purchase_date)，验证 1–714 天无负值。

### 实测画像

- 一次性购买率 **97.00%**（90,557 / 93,358）；复购客户 2,801 人，最高单人 15 单；
- Recency 分布：≤30 天 6,621 / ≤90 天 18,390 / 91–180 天 19,587 / >180 天 55,381（59.3%）。

## 七、用户标签与生命周期分层（dim_customer_segment）

### RFM 数据适配（核心设计）

97% 客户一次性购买，F 维度若机械五等分会失去区分度。因此：

- R、M 用分位数评分（阈值数据推导：R p20=93/p80=383 天；M p20=55.26/p80=208.55 BRL）；
- F 先分一次性/复购，复购再按频次细分：1单=1 / 2单=2 / 3-4单=3 / 5-9单=4 / ≥10单=5；
- MySQL 8.0 无 PERCENTILE_CONT，改用 ROW_NUMBER 取第 CEIL(q×n) 行实现分位数（并列按 customer_unique_id 确定性排序）。

### 四维标签

| 维度 | 规则要点 |
| --- | --- |
| 价值 | high ≥ p80（18,675 人）/ mid（56,014）/ low < p20（18,669），精确 20/60/20 |
| 生命周期 | new（≤30 天且单订单 6,414）/ active ≤90（11,976）/ at_risk ≤180（19,587）/ churned >180（55,381）；按规则阈值划分，未通过预测模型或实验优化 |
| 行为 | 6 个布尔标签（one_time/repeat/high_aov/price_sensitive/category_focused/installment_user）+ 主标签优先级级联 |
| 履约体验 | service_recovery_needed（延迟≥1 且均分≤2）/ low_satisfaction / frequent_delay / delivery_delayed / delivery_normal |

### 最终业务人群（8 类，互斥）

履约受损 4,024 / 高价值活跃 3,666 / 高价值流失风险 3,761 / **高价值已流失 10,326** / 重复购买成长 510 / 首购未复购 28,521 / 低价值长期沉默 10,837 / 其他 31,713。验证：各人群之和 = 93,358 ✓。

技术亮点：用 MySQL 8 的 `LATERAL` 子查询实现规则级联"命中即停"，保证每人恰好一条互斥标签。

## 八、Cohort 留存分析

### 观察窗口截断处理

- Cohort 按首笔 delivered 订单月份划分（2016-09 ~ 2018-07 共 22 个）；活跃 = 当月有 delivered 订单；
- analysis_date 所在的 2018-08 为不完整月份，观察终点取最后完整月 2018-07（由数据推导，非硬编码）；
- **可观察格子全量生成**（当月没有留存客户时记 0）；**不可观察格子不生成行**（不把未来月份当 0 留存）；
- 覆盖范围勾稽：首购在 2018-08 的 6,144 人无法观察完整 M0，不进入 Cohort；87,214 + 6,144 = 93,358 ✓。

### 零留存与缺失值处理

采用"完整可观察网格 + 左关联"结构，保留零留存格子。只生成有留存行为的行会遗漏真实零值，使汇总留存率偏高。

### 实测结果（SQL 与 Python 双端一致）

| 指标 | 成熟 Cohort 数 | 汇总口径 | 留存率 |
| --- | --- | --- | --- |
| M1 | 21 | **ΣM1 留存客户数 / ΣCohort Size = 390 / 81,265** | **0.48%** |
| M2 | 20 | 成熟 Cohort 简单平均 | 0.29% |
| M3 | 19 | 成熟 Cohort 简单平均 | 0.21% |

产出：cohort_retention_long.csv（255 行）、cohort_retention_matrix.csv、留存热力图（不可观察格子留白）。验证：22 个 Cohort 的 M0 均为 100% ✓。

## 九、履约体验分析

### 样本口径

delivered 且签收/预计时间齐全且有评价的订单：95,364 笔（与订单宽表勾稽一致）。

### 实测结果（SQL 与 Python 双端完全一致）

| 指标 | 数值 |
| --- | --- |
| 延迟率 | 7.98%（7,613 / 95,364） |
| 准时 / 延迟平均评分 | 4.30 / 2.57 |
| 评分下降比例 | **40.24%** |
| 低评分率：准时 vs 延迟 | 9.15% vs 53.99% |
| 分段均分 1-3/4-7/8-14/15+ 天 | 3.60 / 2.11 / 1.67 / 1.72 |
| 高价值客户延迟后均分 | 2.46（与全体 2.57 相近，高价值客户并未更宽容） |
| 州延迟率 | AL 23.21% 最高，RO 2.93% 最低（东北部普遍偏高） |

### 统计检验（三重证据链）

1. 卡方检验（延迟×低评分）：χ²=12,670.16，p<0.001，Cramér's V=0.3645（中等偏强关联）；
2. Mann–Whitney U（评分为有序分类不满足正态假设，选非参数检验）：p<0.001；
3. **控制变量逻辑回归**：`is_low_score ~ is_delayed + ln(订单金额+1) + 州哑变量 + 主类别哑变量`，延迟 OR=11.35（95% CI 10.78–11.95），p<0.001——控制已观测变量后关联仍显著。

**结论与限制**：配送延迟与较低评分显著相关；观察性数据无法排除全部未观测混淆因素，不构成因果证据。

## 专题分析：首购后 90 天二购驱动因素

### 口径与观察窗口

- 客户主体为 `customer_unique_id`，首购和二购均限定为 `delivered`；
- 二购必须发生在首购后的另一个自然日且不晚于第 90 天，同日订单排除，以降低拆单或同次购物会话干扰；
- 首购截止日为 2018-06-01，保证每名客户都有完整 90 天观察窗；成熟样本 75,563 人。

### 实测结果

| 指标 | 结果 |
| --- | ---: |
| 90 天跨日二购客户 / 二购率 | 980 人 / **1.2969%** |
| 二购间隔中位数 | 29.00 天 |
| 多商品首单（完整体验样本） | OR=1.4099，95% CI 1.1349–1.7515，p=0.0019 |
| 首单低评分（完整体验样本） | OR=0.7371，95% CI 0.5835–0.9311，p=0.0105 |
| 首单配送延迟（完整体验样本） | OR=0.9127，95% CI 0.6890–1.2090，p=0.5242，未显著 |

购买时模型覆盖 75,563 人；首单体验模型仅使用配送与评分均可观察的 74,820 人。两层模型均控制州、主品类和首购月份，并使用 HC1 稳健标准误。评价缺失不作为驱动变量，所有结果只解释为条件关联。

## 十三、核心结论汇总

1. **一次性购买主导**：97.00% 客户只买一次，21 个成熟 Cohort 的加权 M1 留存率仅 0.48%——Olist 的客户结构以一次性购买为主，首购培育是明确的运营重点；
2. **90 天跨日二购稀缺**：成熟首购客户二购率为 1.2969%；多商品首单与二购正向关联，首单低评分与二购负向关联，但均不能解释为因果；
3. **高价值流失人群值得优先评估**：10,915 人贡献历史支付的 30.89%，可作为召回实验候选；历史支付贡献不等于可挽回收入；
4. **履约体验是满意度的强相关因素**：延迟订单评分下降 40.24%，控制地区/类别/金额后 OR=11.35 仍显著；
5. **可执行的运营抓手**：71,424 人分层名单 + 优先级排期；两个 A/B 实验设计提供验证增量效果的下一步路径。

## 十五、关键建模与工程注意事项

| # | 风险 | 处理方式 |
| --- | --- | --- |
| 1 | CSV 评价文本含内嵌换行，wc -l 统计行数虚高 5,495 | 统计 CSV 记录数必须用解析器 |
| 2 | 物理行数、记录数与唯一 ID 数混淆 | 分别检查 CSV 解析记录数、主键重复与订单覆盖 |
| 3 | 先筛异常再计算占比，使分母范围错误 | 聚合占比的分母必须是检查范围，而非异常结果集 |
| 4 | 复购客户数（2,997）与多余 ID 数（3,345）混淆 | 明确计数对象及订单状态范围 |
| 5 | 时间链路异常被无差别排除 | 对照指标所用字段处理；delivery_days/delay_days 不使用审批与承运商时间 |
| 6 | Cohort 漏掉零留存格子导致汇总偏高 | 全量生成可观察格子，未来月份留空 |
| 7 | 数据库批量文件导入受环境配置影响 | 使用 pandas 解析与批量插入路径 |
| 8 | MySQL 8.0 无 PERCENTILE_CONT | 用 ROW_NUMBER 取位点实现分位数，并列键保证确定性 |
| 9 | UNION 两侧排序规则冲突 | 字面量与表列混用时显式指定 COLLATE |
| 10 | 当天超时订单（delay_days=0 但 is_delayed=1）落不进分段 | 边界值要枚举测试 |

## 十七、项目限制

1. 数据来自历史公开数据，不代表当前 Olist 实际经营状态；
2. 无真实营销触达记录，只能设计 A/B 测试，不能报告真实增量效果；
3. 复购与流失定义受观察窗口限制（观察日 2018-08-30）；

5. 90 天二购模型同样只识别条件关联，且不计观察窗之外的后续购买；
6. 缺成本数据，无法计算利润或真实 CLV；
7. 画像仅基于交易/履约/评价数据，缺浏览与点击行为。
