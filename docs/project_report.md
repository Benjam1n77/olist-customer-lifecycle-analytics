## 一、项目概述

### 1.1 背景与目标

基于 Kaggle 公开数据集 Brazilian E-Commerce Public Dataset by Olist（实际购买时间覆盖 2016 年 9 月 – 2018 年 8 月，99,441 笔订单），独立完成一个可复现、可展示的数据分析项目，回答七个业务问题：

| # | 业务问题 | 最终答案（实测） |
| --- | --- | --- |
| 1 | 一次性购买是否严重 | 是，一次性购买占比 97.00% |
| 2 | 首购后留存表现 | 21 个成熟 Cohort 的加权 M1 留存率为 0.48%（390 / 81,265） |
| 3 | 高价值流失用户 | 10,915 人，历史支付占比 30.89% |
| 4 | 配送延迟是否影响评分 | 延迟订单评分下降 40.24%，控制混淆后关联仍显著（OR=11.35） |
| 5 | 首购后 90 天二购的关联因素 | 成熟客户跨日二购率 1.2969%；多商品正向关联、首单低评分负向关联 |
| 6 | 营销人群名单 | 6 条互斥规则产出 71,424 人分层名单 |
| 7 | 看板与实验支持 | 3 页 Tableau 看板数据 + 2 个 A/B 测试设计 |

## 四、阶段 3：数据导入与质量检查

### 4.1 数据导入

- 初版设计用 `LOAD DATA LOCAL INFILE`（最快），但本机 MySQL 的 `secure_file_priv` 安全设置禁止，改为 **pandas 读取 + executemany 批量插入**（每 5,000 行一批），全部数据约 1 分 20 秒导入完成；
- **两个重要发现**：
  1. `olist_order_reviews_dataset.csv` 的评价文本含**内嵌换行符**：物理行数 104,719 ≠ 实际记录数 99,224。教训：**统计 CSV 行数必须用解析器，不能用 wc -l**；
  2. CSV 中存在 **789 个重复 review_id**——深入核查发现每对重复除 order_id 外所有字段完全一致、100% 属同一真实客户、98.5% 两单购买时间相差 ≤30 天，判定为"同一评价问卷被平台关联到两笔订单"（非用户重复提交，因为重复提交必然产生不同 review_id 与时间戳）。用 `INSERT IGNORE` 保留首条，被丢弃的 814 行留档至 `data/interim/dropped_duplicate_reviews.csv` 供审计。

### 4.2 质量检查（36 项）

编写 `sql/03_data_quality_checks.sql`，覆盖主键唯一性 / 空值 / 枚举值 / 时间逻辑 / 数值合理性 / 关联完整性 / 多重记录七大类，产出 `docs/data_quality_report.md` 与 `outputs/tables/data_quality_summary.csv`。

主要结论：

| 检查类 | 结果 |
| --- | --- |
| 主键唯一性 | 全部通过 |
| 关联完整性 | 100%（0 个孤立记录） |
| 有效订单 | delivered 96,478 笔（97.02%） |
| 时间逻辑 | D2 审批晚于承运 1,350 条（1.40%）；经核实 delivery_days/delay_days 不使用审批/承运商时间，故不排除，仅记录 |
| 数值合理性 | 9 条支付金额≤0、4 件商品重量≤0，排除 |
| 金额口径 | item_amount 与 payment_amount 存在 260 笔差异>0.05 元——证实 Brief"不得假设相等"的必要性 |

### 4.3 本阶段的自我纠错

- 修复质量检查 SQL 中 D/E 系列百分比分母错误（WHERE 先筛出异常行再用窗口函数求分母，导致百分比恒为 100%；改为 `SUM(布尔条件)/COUNT(*)`）；
- 纠正复购口径混淆：**复购客户 2,997 人**，3,345 是"多余 customer_id 数"（一人 3 单贡献 2 个多余 ID），两者不可混用；
- 细化签收时间空值结论：2,965 条空值中仅 8 条属 delivered 订单（真异常），其余 2,957 条是未交付订单的正常现象。

## 五、阶段 4：订单粒度宽表（mart_order_summary）

### 做了什么

严格遵循"先聚合再 JOIN"原则（商品/支付/评价对订单均为一对多，直接 JOIN 会行数膨胀）：

1. `sql/04` → `order_item_agg`（98,666 行）：item_count、distinct_product_count、seller_count、goods/freight/item_amount、main_category（商品金额最高的类别，并列取字典序保证确定性）；
2. `sql/05` → `order_payment_agg`（99,440 行）：payment_amount、main_payment_type、max_installments；
3. `sql/06` → `order_review_agg`（98,167 行）：同单多评价（243 单）取最高分，规则写入注释与指标文档；
4. `sql/07` → `mart_order_summary`（99,441 行 × 32 字段，一行一订单），含 delivery_days / delay_days / is_delayed / is_low_score 派生字段。

### 验证

- 粒度：99,441 行 = orders 行数，一行一订单 ✓；
- 金额：支付总额聚合前后精确一致（16,008,872.12 BRL）✓；
- Brief 3.3 金额差异检查：98,665 笔双金额齐全订单中 98,089 笔完全相等，260 笔差异>0.05 元（241 笔支付偏多、19 笔偏少，最大差 182.81 元），已量化记录。

### 自我纠错

自查发现 1,267 笔"当天超时"订单（时间戳晚于预计但日期相同，delay_days=0）落不进延迟分段，补充规则归入 1-3 天档。

## 七、阶段 6：用户标签与生命周期分层（dim_customer_segment）

### RFM 数据适配（核心设计）

97% 客户一次性购买，F 维度若机械五等分会失去区分度。因此：

- R、M 用分位数评分（阈值数据推导：R p20=93/p80=383 天；M p20=55.26/p80=208.55 BRL）；
- F 先分一次性/复购，复购再按频次细分：1单=1 / 2单=2 / 3-4单=3 / 5-9单=4 / ≥10单=5；
- MySQL 8.0 无 PERCENTILE_CONT，改用 ROW_NUMBER 取第 CEIL(q×n) 行实现分位数（并列按 customer_unique_id 确定性排序）。

### 四维标签

| 维度 | 规则要点 |
| --- | --- |
| 价值 | high ≥ p80（18,675 人）/ mid（56,014）/ low < p20（18,669），精确 20/60/20 |
| 生命周期 | new（≤30 天且单订单 6,414）/ active ≤90（11,976）/ at_risk ≤180（19,587）/ churned >180（55,381）；采用 Brief 初始规则，与 Recency 分布自然对齐故未调整 |
| 行为 | 6 个布尔标签（one_time/repeat/high_aov/price_sensitive/category_focused/installment_user）+ 主标签优先级级联 |
| 履约体验 | service_recovery_needed（Brief 示例规则：延迟≥1 且均分≤2）/ low_satisfaction / frequent_delay / delivery_delayed / delivery_normal |

### 最终业务人群（8 类，互斥）

履约受损 4,024 / 高价值活跃 3,666 / 高价值流失风险 3,761 / **高价值已流失 10,326** / 重复购买成长 510 / 首购未复购 28,521 / 低价值长期沉默 10,837 / 其他 31,713。验证：各人群之和 = 93,358 ✓。

技术亮点：用 MySQL 8 的 `LATERAL` 子查询实现规则级联"命中即停"，保证每人恰好一条互斥标签。

## 八、阶段 7：Cohort 留存分析

### 观察窗口截断处理（本阶段核心难点）

- Cohort 按首笔 delivered 订单月份划分（2016-09 ~ 2018-07 共 22 个）；活跃 = 当月有 delivered 订单；
- analysis_date 所在的 2018-08 为不完整月份，观察终点取最后完整月 2018-07（由数据推导，非硬编码）；
- **可观察格子全量生成**（留存为 0 也记 0，是真实流失）；**不可观察格子不生成行**（绝不把未来月份当 0 留存）；
- 副作用及勾稽：首购在 2018-08 的 6,144 人无法观察 M0，不进入 Cohort；87,214 + 6,144 = 93,358 ✓。

### 自我纠错

初版只生成"有留存行为"的行，会导致 M1/M2/M3 平均值虚高（0 留存的格子被漏掉）；重写为"网格 + 左关联"结构修复。

| --- | --- | --- | --- |

## 九、阶段 8：履约体验分析

### 样本口径

delivered 且签收/预计时间齐全且有评价的订单：95,364 笔（与订单宽表勾稽一致）。

### 实测结果（SQL 与 Python 双端完全一致）

| 指标 | 数值 |
| --- | --- |
| 延迟率 | 7.98%（7,613 / 95,364） |
| 准时 / 延迟平均评分 | 4.30 / 2.57 |
| 评分下降比例 | **40.24%** |
| 低评分率：准时 vs 延迟 | 9.15% vs 53.99% |
| 分段均分 1-3/4-7/8-14/15+ 天 | 3.60 / 2.11 / 1.67 / 1.72 |
| 高价值客户延迟后均分 | 2.46（与全体 2.57 相近，高价值客户并未更宽容） |
| 州延迟率 | AL 23.21% 最高，RO 2.93% 最低（东北部普遍偏高） |

### 统计检验（三重证据链）

1. 卡方检验（延迟×低评分）：χ²=12,670.16，p<0.001，Cramér's V=0.3645（中等偏强关联）；
2. Mann–Whitney U（评分为有序分类不满足正态假设，选非参数检验）：p<0.001；
3. **控制变量逻辑回归**（应要求补充实现）：`is_low_score ~ is_delayed + ln(订单金额) + 州哑变量 + 主类别哑变量`，延迟 OR=11.35（95% CI 10.78–11.95），p<0.001——控制混淆后关联依然稳健。

**结论表述克制**：只说"配送延迟与较低评分显著相关"，不断言因果（观察性数据无法排除全部未观测混淆因素）。

## 专题分析：首购后 90 天二购驱动因素

### 口径与观察窗口

- 客户主体为 `customer_unique_id`，首购和二购均限定为 `delivered`；
- 二购必须发生在首购后的另一个自然日且不晚于第 90 天，同日订单排除，以降低拆单或同次购物会话干扰；
- 首购截止日为 2018-06-01，保证每名客户都有完整 90 天观察窗；成熟样本 75,563 人。

### 实测结果

| 指标 | 结果 |
| --- | ---: |
| 90 天跨日二购客户 / 二购率 | 980 人 / **1.2969%** |
| 二购间隔中位数 | 29.00 天 |
| 多商品首单（完整体验样本） | OR=1.4099，95% CI 1.1349–1.7515，p=0.0019 |
| 首单低评分（完整体验样本） | OR=0.7371，95% CI 0.5835–0.9311，p=0.0105 |
| 首单配送延迟（完整体验样本） | OR=0.9127，95% CI 0.6890–1.2090，p=0.5242，未显著 |

购买时模型覆盖 75,563 人；首单体验模型仅使用配送与评分均可观察的 74,820 人。两层模型均控制州、主品类和首购月份，并使用 HC1 稳健标准误。评价缺失不作为驱动变量，所有结果只解释为条件关联。

## 十三、核心结论汇总

1. **一次性购买主导**：97.00% 客户只买一次，21 个成熟 Cohort 的加权 M1 留存率仅 0.48%——Olist 的客户结构以一次性购买为主，首购培育是明确的运营重点；
2. **90 天跨日二购稀缺**：成熟首购客户二购率为 1.2969%；多商品首单与二购正向关联，首单低评分与二购负向关联，但均不能解释为因果；
3. **高价值客户流失是最大的收入漏洞**：高价值流失 10,915 人，占历史支付 30.89%，召回具有明确优先级；
4. **履约体验是满意度的强相关因素**：延迟订单评分下降 40.24%，控制地区/类别/金额后 OR=11.35 仍显著；
5. **可执行的运营抓手**：71,424 人分层名单 + 优先级排期；两个 A/B 实验设计提供验证增量效果的下一步路径。

## 十五、踩坑与经验教训

| # | 问题 | 教训 |
| --- | --- | --- |
| 1 | CSV 评价文本含内嵌换行，wc -l 统计行数虚高 5,495 | 统计 CSV 记录数必须用解析器 |
| 2 | review_id 重复最初误判为 6,309 个 | 行数差异要先拆解构成再下结论；所有判断用数据证据链验证 |
| 3 | 质量检查 SQL 百分比分母错误（先 WHERE 筛异常再窗口求和） | 聚合占比的分母必须是"检查范围"而非"异常结果集" |
| 4 | 复购客户数（2,997）与多余 ID 数（3,345）混淆 | 计数类指标必须写清"数的是什么对象" |
| 5 | D2/D3 处理策略最初写成"排除出 delivery_days" | 处理策略必须对照指标的实际计算公式，这两个指标根本不用审批/承运商时间 |
| 6 | Cohort 初版漏掉 0 留存格子导致均值虚高 | 留存网格必须全量生成可观察格子 |
| 7 | LOAD DATA LOCAL INFILE 被 secure_file_priv 禁止 | 先验证环境能力再选技术方案，准备好降级路径 |
| 8 | MySQL 8.0 无 PERCENTILE_CONT | 用 ROW_NUMBER 取位点实现分位数，并列键保证确定性 |
| 9 | UNION 两侧排序规则冲突 | 字面量与表列混用时显式指定 COLLATE |
| 10 | 当天超时订单（delay_days=0 但 is_delayed=1）落不进分段 | 边界值要枚举测试 |

## 十七、项目限制（诚实声明）
